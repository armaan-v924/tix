The directories inside a ticket are **git worktrees** — additional working
directories attached to a repository you already have.

```
~/code/api                  your checkout, on main, untouched
~/tickets/JIRA-123/api      a worktree of it, on its own branch
```

They share the repository's object store, remotes, and branches: a fetch in
one is visible in the other, and a branch created in the worktree is a real
branch in `~/code/api`. They do not share the checkout — different branch,
different index, different uncommitted changes.

So starting a ticket never switches branches in your main checkout, never
stashes, and does not care whether it is dirty, diverged, or on some other
branch. Several tickets can hold branches of the same repository at once.

The flip side: nothing fast-forwards your main checkout either. Its local
`main` goes as stale as you leave it — tix branches from what it fetches,
not from what you have checked out.

## Each worktree has its own branch

A ticket does not have "a branch". Each worktree records its own:

```toml
[ticket.worktrees.api]
repo = "api"
branch = "feature/JIRA-123-fix-the-login-bug"

[ticket.worktrees.web]
repo = "web"
branch = "feature/JIRA-123-fix-the-login-bug"
```

Those names match because they were derived from the same key at the same
moment, but they are branches in *different repositories* and nothing keeps
them in step afterwards. Worktrees in a ticket share a branch **prefix**,
not a branch.

<Aside type="caution" title="A worktree added later can differ">
`tix ticket add` derives the name at *add* time, against whatever
`branch_prefix` says then. Pass `--branch` to say exactly what you want.
</Aside>

## Where a branch starts

A new branch is cut from a **base**. Left alone, that is the repository's own
default branch on origin — `origin/main`, `origin/master`, `origin/trunk`,
whatever origin's `HEAD` points at — fetched first, so it is fresh. Each
repository answers for itself, so one ticket can span a `main` repo and a
`master` repo with no flags.

`--base` on `tix setup` and `tix add` picks something else:

```sh
tix add api --base release/2.4            # a branch, local or origin's
tix add api --base origin/release/2.4     # exactly origin's
tix add api --base v2.4.0                 # a tag, a SHA, any ref
```

A bare branch name is fetched, then resolved between your local branch and
origin's by which one is ahead:

| local vs `origin/<b>` | base |
| --- | --- |
| behind or equal | `origin/<b>` — always cut from fresh |
| ahead | `<b>` — the unpushed commits *are* the base |
| only one exists | that one |
| diverged | an error naming both; qualify it |

Anything qualified — `origin/<b>`, `refs/heads/<b>`, a tag, a SHA — resolves
literally. If the fetch fails (offline, say), tix warns and resolves against
the refs you already have.

The base is recorded beside the branch, as a ref name rather than a SHA,
because a name is what a pull request's base takes:

```toml
[ticket.worktrees.api]
repo = "api"
branch = "feature/JIRA-123-fix-the-login-bug"
base = "origin/main"
```

A branch that already exists is checked out as it is, never moved. Without
`--base` it records no base — tix did not cut it, so it cannot say from what.
With `--base`, the branch must already contain that base, or the add errors.

### Stacking

A base can be a branch checked out in a sibling worktree, unpushed commits
and all — which is what a stacked change is:

```sh
tix add api --as api-part2 --branch stack/JIRA-123-part-2 \
    --base feature/JIRA-123-fix-the-login-bug
```

```toml
[ticket.worktrees.api-part2]
repo = "api"
branch = "stack/JIRA-123-part-2"
base = "feature/JIRA-123-fix-the-login-bug"
```

Git only remembers the merge-base; the recorded `base` is what lets a plugin
tell this branch from one cut off `main`.

## How the name is derived

```
<branch_prefix>/<key>-<sanitized description>
```

The description is lowercased, runs of non-alphanumeric characters collapse
to a single `-`, the ends are trimmed, and the result is capped at 40
characters.

| Prefix | Key | Description | Branch |
| --- | --- | --- | --- |
| `feature` | `JIRA-123` | `Fix the Login Bug!` | `feature/JIRA-123-fix-the-login-bug` |
| `feature` | `JIRA-123` | *(none)* | `feature/JIRA-123` |
| *(none)* | `JIRA-123` | `Retry logic` | `JIRA-123-retry-logic` |
| `feature` | `JIRA-123` | `!!!` | `feature/JIRA-123` |

Each part drops out cleanly when absent. This happens once, at creation —
see [creation-time seeds](../seeds/).

## Several worktrees of one repository

One worktree per repository is the common case, and its directory is named
after the repository alias. When one ticket needs two branches of the same
repository open side by side, the second worktree goes under its own name:

```sh
tix add api --as api-auth-spike --branch spike/JIRA-123-auth
```

<FileTree>
- ~/tickets/JIRA-123
  - api               on feature/JIRA-123-fix-the-login-bug
  - api-auth-spike    on spike/JIRA-123-auth
</FileTree>

Both flags are needed there, and neither is guessed: `api` is taken as a
directory name, and the branch `api` holds cannot be checked out twice.

Each is required only when its own default is unusable — `--as` when a
worktree already occupies that directory, `--branch` when a worktree of the
same repository already has the derived branch. Nothing about a repository
appearing twice is special in itself, so `tix add api` after a
`tix remove api` takes the free name and the derived branch back with no
flags at all.

```toml
[ticket.worktrees.api]
repo = "api"
branch = "feature/JIRA-123-fix-the-login-bug"

[ticket.worktrees.api-auth-spike]
repo = "api"
branch = "spike/JIRA-123-auth"
```

Everything downstream addresses the **name**, not the alias: `tix remove
api-auth-spike` takes that worktree alone, `tix info` lists both under
`api`, and a plugin run from inside either one is told `--tix-repo api`
with the `--tix-repo-dir` of the worktree you are actually in.

## Branches are yours

tix creates a branch when a worktree needs one and records the name. It will
not rename, rebase, push, or delete one. `tix destroy` removes working
directories; branches and commits stay.
