With no flag, ticket-scoped commands walk upward from the working directory
looking for a `.tix/ticket.toml`. Nearest one wins.

```
~/tickets/JIRA-123/.tix/ticket.toml     ← found
~/tickets/JIRA-123/api/src/handlers/    ← you are here
```

Any directory inside a ticket is inside that ticket, at any depth.

The walk follows the **logical** working directory rather than resolving
symlinks, so tix agrees with git about where you are. It matches the file,
not the `.tix/` directory. It stops at a filesystem boundary. It is not
limited to your tickets directory — a ticket found elsewhere still works.

## Overriding it

`--ticket` skips the walk. Its argument is read as one of two forms, by
shape:

| You write | Read as | Resolves to |
| --- | --- | --- |
| `JIRA-123` | id | `tickets_directory/JIRA-123` |
| `./JIRA-123` | path | that directory, relative to where you are |
| `../other`, `/abs/path`, `.` | path | that directory |

A bare name is **always** an id. Anything with a path separator, or `.` /
`..`, is a path.

<Aside type="caution" title="The one that catches people">
A ticket directory sitting in your working directory still has to be written
`./JIRA-123`. Bare, it resolves against your tickets directory instead.
</Aside>

## Both forms are assertions

`--ticket` asserts *this is a ticket root*. Pointing it at a subdirectory is
an error:

```sh
tix info --ticket ./JIRA-123/api
# error: not a ticket root
```

Otherwise a typo would resolve to something plausible instead of failing.

## Destroy takes it positionally

```sh
tix destroy JIRA-123      # id form
tix destroy ./JIRA-123    # path form
```

Read the same two ways, and conflicts with `--ticket` — pass one or the
other. It exists because destroying a ticket is usually done from outside it.
