Anything `tix` does not recognise, it treats as a plugin:

```sh
tix deploy staging
```

With no built-in `deploy`, tix runs `tix-deploy` from your `PATH`, passing
the arguments along with the context it already resolved — which ticket you
are in, where the config lives, what output format you asked for.

Same pattern as git and cargo. There is no registry and no install step:
putting `tix-deploy` on your `PATH` is the installation.

## Built-ins always win

A `tix-add` on your `PATH` does not shadow `tix add`. Plugins are also
top-level only — `tix deploy` can be a plugin, `tix ticket deploy` cannot.

Installed plugins are listed in `tix --help`, which is the only time tix
goes looking for them.

## Configuration

A plugin may keep its own table in either document, named after it:

```toml
[deploy]
environment = "staging"
```

tix does not read, validate, or rewrite it, and it survives every write tix
makes.

<Aside type="danger" title="Plugins run as you">
tix makes no safety guarantees about third-party plugins. A plugin is an
arbitrary program running with your permissions, and `tix <anything>` will
run one that matches the name.
</Aside>

## Writing one

The contract is in the
[plugin specification](https://github.com/armaan-v924/tix/blob/main/PLUGIN_SPEC.md).
There are SDKs for both languages: `tix-sdk` for Rust, with
[API docs](/crates/tix_sdk/), and `pytix.host` for Python.
