A tix plugin is an executable named `tix-<name>` on `PATH`. `tix foo` execs
the first `tix-foo` it finds, git/cargo-style. Builtins always win, and
plugins are top-level commands only. A Python plugin ships a
`console_scripts` entry point named `tix-<name>`.

Both languages have an SDK that implements this document: `tix-sdk` in Rust
([API docs](/crates/tix_sdk/)), `pytix.host` in Python.

<Aside type="danger">
tix makes no safety guarantees about third-party plugins. A plugin is an
arbitrary program running as you.
</Aside>

## 1. The exec contract

When the user runs `tix <name> <args…>`, the host execs:

```sh frame="none"
tix-<name> --tix-protocol <int> \
           --tix-config <path> \
           [--tix-ticket <path>] \
           --tix-delta <path> \
           [--tix-repo <alias>] [--tix-repo-dir <path>] \
           --tix-log-level <level> \
           --tix-output <json|toml|default> \
           --tix-color <bool> \
           <user args>
```

| Flag | Presence | Meaning |
| --- | --- | --- |
| `--tix-protocol` | always | The [protocol integer](../protocol/). |
| `--tix-config` | always | Path to the global config file — the real file on disk. |
| `--tix-ticket` | only inside a ticket | Path to the **ticket directory** (parent of `.tix/`). Its absence is meaningful: commands that create tickets run without one. |
| `--tix-delta` | always | Host-created temp file for your outbound config delta ([§3](#3-config-access)). stdout is yours, for the user. Writing no file changes nothing. |
| `--tix-repo` / `--tix-repo-dir` | when cwd is inside a repo worktree | Alias and path of that worktree (longest-prefix match of cwd against the ticket's worktrees). |
| `--tix-log-level` | always | The host's **resolved** level — it already collapsed `-v`/`-q`/`--log-level`. Do not reimplement that precedence. |
| `--tix-output` | always | Resolved output format, so `tix foo --json \| jq` works through you. |
| `--tix-color` | always | Resolved from TTY detection and `NO_COLOR`, per-process. |

Rules:

- The **entire `--tix-*` prefix is reserved** for the host. Everything else
  in argv is the user's args, forwarded in order and untouched.
- **Ignore unknown `--tix-*` flags.** Additions never bump the protocol;
  checking whether a flag arrived is capability detection.
- Paths are real files, so you can hand-run a plugin for debugging:
  `tix-foo --tix-protocol 1 --tix-config ./test.toml …`
- stdout, stderr, and stdin are inherited — you own the terminal. Prompt,
  color, and stream as you please, honoring `--tix-color`.
- Exit codes propagate unmodified, except **125**
  ([protocol versions](../protocol/)).
- `TIX_DEPTH` is set and incremented on every dispatch and hard-fails past
  10 — the fork-bomb guard for plugins that shell back out to `tix`.

The SDK does all of it in one call:

<Tabs syncKey="language">
<TabItem label="Rust">
```rust
let host = tix_sdk::host::HostContext::from_env_or_exit("one-line description");
// host.config_path, host.ticket_root, host.delta_path, host.user_args, …
```
[`tix-sdk/examples/toy-plugin.rs`](https://github.com/armaan-v924/tix/blob/main/tix-sdk/examples/toy-plugin.rs)
is a complete working plugin.
</TabItem>
<TabItem label="Python">
```python
context = pytix.host.HostContext.from_env_or_exit("one-line description")
# context.config_path, context.ticket_root, context.user_args, …
```
</TabItem>
</Tabs>

## 2. Protocol version

`--tix-protocol` is a monotonic integer, independent of any crate version,
and the only compatibility boundary between host and plugin. On mismatch,
exit **125** with a rebuild message — the SDK does both for you. The host
reserves 125 for this and reports a versioning problem rather than a plugin
crash; a plugin exiting 125 for its own reasons will be misreported.

See [protocol versions](../protocol/) for the version-to-change table.

## 3. Config access

Two TOML documents exist: the global config and the ticket document
(`<ticket>/.tix/ticket.toml`). Each is a set of sections, one table per
consumer. Your plugin owns the `[<name>]` table in either document, and its
schema is entirely yours — tix never deserializes it.

**Reads** go through the SDK's document layer: parse generically, extract
your section by type.

<Tabs syncKey="language">
<TabItem label="Rust">
```rust
let doc = tix_sdk::document::TixDocument::load(&host.config_path)?;
let mine: MyConfig = doc.section_or_default("myplugin")?;
```
</TabItem>
<TabItem label="Python">
```python
context = pytix.host.HostContext.from_env_or_exit("what my plugin does")
mine = context.config_section("myplugin") or {}
```

Python gets plain `dict`s, typed as `tomllib` would type them: tables are
`dict`, arrays are `list`, TOML datetimes are `datetime`.
</TabItem>
</Tabs>

A missing section is normal on a first run, which is why `section()` returns
an `Option` in Rust and `None` in Python, and why `section_or_default()`
exists.

**Writes** never touch the files directly. The host is the single writer:
you emit a *delta* into the `--tix-delta` file, and the host applies it after
you exit **0**.

<Tabs syncKey="language">
<TabItem label="Rust">
```rust
tix_sdk::delta::Delta::new(DeltaTarget::Ticket)
    .set("myplugin.branch", "main")?
    .write_to(host.delta_path.as_deref().unwrap())?;
```
</TabItem>
<TabItem label="Python">
```python
delta = pytix.host.Delta("ticket")
delta.set("myplugin.branch", "main")
context.write_delta(delta)
```
</TabItem>
</Tabs>

On the wire it is JSON:

```json
{"target": "ticket", "ops": [{"set": "myplugin.branch", "value": "main"}]}
```

- `target` is `"global"` or `"ticket"`. Ops are ordered; overlapping keys are
  last-writer-wins.
- Values map to TOML by their JSON text form (`1` is an integer, `1.0` a
  float). Datetime — the one type JSON lacks — uses the tagged form
  `{"$datetime": "2026-07-19T09:00:00Z"}`. `pytix` applies the tag for you:
  pass a `datetime`, `date`, or `time`.
- The host applies against a **fresh parse**, so your delta merges with
  anything written while you ran. It then revalidates the sections it owns
  (`[engine]`, `[cli]`, `[defaults]`, `[ticket]`); a delta that breaks one is
  rejected wholesale and nothing is written. Your own section passes
  unvalidated.
- Writes outside your own section are allowed but unsupported.
- Nonzero exit, no file, or an empty file writes nothing.

Diff-back is not an RPC channel. Everything else — creating worktrees,
syncing, resolving tickets — goes directly through `tix-sdk → tix-engine` in
your own process; git operations carry no single-writer constraint.

## 4. Plugin state vs. plugin config

**Config** is human-editable settings: your `[<name>]` table, read via
section accessors, written via diff-back ([§3](#3-config-access)).

**State** is caches and derived data of any shape or size — plain files in a
directory, with no document, delta, or protocol involved.

<Tabs syncKey="language">
<TabItem label="Rust">
```rust
let dir = tix_sdk::state::ticket_state_dir(host.require_ticket()?, "myplugin")?;
let cache = tix_sdk::state::cache_dir("myplugin")?;
```
</TabItem>
<TabItem label="Python">
```python
directory = context.state_dir("myplugin")
cache = pytix.host.cache_dir("myplugin")
```
</TabItem>
</Tabs>

Directories are created lazily. Per-ticket state lives at
`<ticket>/.tix/plugins/<name>/`; the cache location wraps the platform cache
directory.

## 5. Nested `tix` invocations

You may shell out to `tix`. Two hazards:

The nested host re-discovers the ticket **from cwd**, which you may have
changed. To mean "the same ticket", pin it:

<Tabs syncKey="language">
<TabItem label="Rust">
```rust
let mut cmd = tix_sdk::spawn::tix_command(host.require_ticket()?);
cmd.args(["ticket", "info"]);
```
</TabItem>
<TabItem label="Python">
```python
subprocess.run(["tix", "--ticket", context.require_ticket(), "ticket", "info"])
```

There is no Python wrapper — the pin is one argument, and spelling it out is
clearer than a binding that hides it.
</TabItem>
</Tabs>

And `TIX_DEPTH` caps recursion at 10 ([§1](#1-the-exec-contract)).

Concurrent config writes are safe: deltas apply against fresh parses under
the write lock, degrading to last-writer-wins at key granularity.

## 6. Help integration

Your `--help` is your own; tix never touches it.

`tix --help` lists installed plugins by scanning `PATH` for `tix-*`. To show
a description beside your name, answer the handshake: `tix-<name>
print-cli-help` prints **one line** to stdout and exits 0.

It is invoked **bare**, with no `--tix-*` flags, so handle it before
requiring host flags. The SDK answers it automatically from the description
passed to `HostContext::from_env_or_exit`.

Skipping it is fine — you appear by name. A handshake that errors or hangs is
cut off, and its output is sanitized: control characters stripped, one line,
capped.
