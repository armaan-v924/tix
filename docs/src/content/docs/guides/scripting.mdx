## Output formats

`tix list` and `tix info` take `--output json` or `--output toml`:

```sh
tix list --output json
```

```json
[
  {
    "description": "Fix the login bug",
    "key": "JIRA-123",
    "path": "/home/you/tickets/JIRA-123",
    "worktrees": 1
  }
]
```

```sh
tix info --output json
```

```json
{
  "description": "Fix the login bug",
  "key": "JIRA-123",
  "path": "/home/you/tickets/JIRA-123",
  "worktrees": [
    {
      "branch": "feature/JIRA-123-fix-the-login-bug",
      "name": "api",
      "path": "/home/you/tickets/JIRA-123/api",
      "repo": "api",
      "status": "ok"
    }
  ]
}
```

Keys come out alphabetically sorted.

`status` is `ok`, `missing`, or `not-a-git-repository`. The last two mean the
ticket document records a worktree that is not there any more — worth
checking for rather than assuming.

Add `--status` to `tix info -o json` for a `git` object on each worktree.
The outer `branch` is the recorded branch. When `git.state` is `available`,
the object contains the live `branch`, `detached`, HEAD commit in `head`,
and the `staged`, `unstaged`, and `untracked` path counts. A detached HEAD
has `branch: null`. A path with both staged and unstaged changes counts in
both. The `upstream` object contains `reference`, `ahead`, and `behind`
when its ref is available locally, and is `null` otherwise. Inspection uses
local refs. If a checkout cannot be inspected, its `git.state` is
`unavailable` and `git.error` describes the problem.

Ticket and config inspection and local teardown previews work with readable
documents on read-only filesystems.

`tix config show` also takes both. TOML output is the document as written,
comments and all; JSON output converts the values, since JSON has nowhere to
put comments.

## Ticket mutations

With `-o json`, `setup`, `add`, `remove`, and `destroy` print one result.
`ticket_path` is absolute when the command has resolved the target.
Each worktree result has a name, repo, path, and outcome. Creation results
include the branch and, when resolved, the base ref, commit, and fetch outcome. Failures include an
`error` object with a stable `code` and a human-readable `message`.

```json
{
  "command": "setup",
  "outcome": "partial",
  "ticket_path": "/home/you/tickets/JIRA-123",
  "worktrees": [
    {
      "name": "api",
      "repo": "api",
      "path": "/home/you/tickets/JIRA-123/api",
      "outcome": "created",
      "branch": "feature/JIRA-123",
      "base": "origin/main",
      "base_commit": "a1b2c3d4e5f60123456789abcdef0123456789ab",
      "base_fetch": "fetched"
    },
    {
      "name": "web",
      "repo": "web",
      "path": "/home/you/tickets/JIRA-123/web",
      "outcome": "failed",
      "error": {"code": "git-error", "message": "git error: could not create worktree"}
    }
  ],
  "error": {"code": "operation-failed", "message": "1 of 2 worktrees failed: web — fix the listed problems and run `tix setup --resume <ticket-path>`"}
}
```

The command outcomes are `succeeded`, `partial`, `declined`, and
`failed`. An exit code of 0 can accompany `declined` when a confirmation
is refused, or `partial` when forced teardown completes with a prune
failure. Use the outcome and per-worktree results to decide how to recover.
A worktree outcome of `dropped` means its ticket entry was removed after
the checkout was found missing or invalid.

`base_fetch` is `fetched` when origin was fetched successfully,
`local-fallback` when a fetch failed and existing local refs supplied the
base, and `not-needed` for a lookup with no fetch, such as a full commit SHA.
A reused branch without an explicit base omits all three base fields. When
an explicit base is checked against a reused branch, `base_commit` is the
verified ancestor.

After partial or interrupted setup, use `tix setup --resume <ticket_path>`
to continue the saved plan. Checkouts already created and recorded are
skipped. A verified checkout that setup created before writing its entry is
reported as `adopted`. Its original base may be unknown. An occupied
directory or checkout that disagrees with the saved plan produces a
`setup-conflict` and is left in place. A concurrent ticket mutation or an
occupied root during fresh setup produces `ticket-conflict`.

With `--dry-run -o json`, teardown commands print the preview shape
(`dry_run`, `command`, `would_succeed`, `actions`). A failed preview
includes `error.code` and `error.message`, even if target validation
failed before any action could be planned. CLI argument parsing errors
use stderr and exit 2.

## Streams

Results go to standard output: listings, `--output json`/`toml` documents,
and, in the default format, the paths `tix setup` and `tix add` create, so `cd "$(tix setup PROJ-1 api)"`
works. Everything else goes to standard error, at every log level: status
lines such as `created worktree api on PROJ-1-fix-login` or `removed worktree
api`, warnings (`warning: …`), and errors (`error: …`). This stays parseable:

```sh
tix list --output json --verbose | jq '.[].key'
```

`-q` / `--quiet` drops the status lines and keeps warnings and errors, for
scripts that only want to hear about problems.

## Exit codes

`0` on success, `1` on any error, with `error: <message>` on standard error.

```sh
if tix info --ticket "$key" --output json > /dev/null 2>&1; then
  echo "ticket exists"
fi
```

## Forwarding to plugins

`--output` is passed to plugins as `--tix-output`, so a plugin can honor
the format you asked for.
