Every key tix reads. The tables below are generated from the types tix
parses the files with, so a key that exists is listed here and a key that is
listed exists.

Both documents are TOML, and both are read through a format-preserving
layer: `tix config set` and every command that records state rewrite only
the value they touch. Comments, key order, and whitespace survive, and so do
tables belonging to plugins.

Unknown keys are an error rather than being ignored, so a typo fails loudly
instead of silently doing nothing.

## The global config

Created by `tix config init`. Its location is resolved in this order:

1. `--config <PATH>`
2. `TIX_CONFIG_PATH` — ignored when set but empty
3. the platform config directory — `~/.config/tix/config.toml` on Linux,
   `~/Library/Application Support/tix/config.toml` on macOS

Every command except `tix config init` and `tix cli completions` requires
the file to exist.

### `[cli]`

Where tix puts things. Both keys are required, and `tix config init` asks
for them.

| Key | Type | Description |
| --- | --- | --- |
| `code_directory` | string | Where source repositories are cloned: `tix repo add` derives a new repo's `code_path` as `code_directory/<alias>` (v2 parity). |
| `tickets_directory` | string | Where ticket workspaces are created, and where id-form `--ticket` arguments resolve (`tickets_directory.join(id)`). |

### `[engine]`

The repositories tix knows about. Maintained by `tix repo add` — you
rarely write this section by hand.

| Key | Type | Description |
| --- | --- | --- |
| `configured_repositories` | table of tables | Source repositories registered by the user, keyed by alias.<br />Optional. |

#### `[engine.configured_repositories.<name>]`

Each entry is a table of its own:

| Key | Type | Description |
| --- | --- | --- |
| `code_path` | string | The path to the code directory of the repository. |
| `remote` | string | The remote URL of the repository. |

### `[defaults]`

Values read **once**, when a ticket or worktree is created, and then
recorded in the ticket document. Changing one never rewrites a ticket that
already exists — see [Seeds, not defaults](../../concepts/seeds/).

Every key is optional, and an absent `[defaults]` section is normal.

| Key | Type | Description |
| --- | --- | --- |
| `branch_prefix` | string | Seed for branch name derivation at `tix ticket setup`: `<prefix>/<key>-<sanitized-description>`.<br />Optional. |
| `default_repository_owner` | string | Seed for remote URL construction: the owner used when a repository is given without one.<br />Optional. |
| `github_base_url` | string | Seed for remote URL construction.<br />Optional. |
| `repositories` | array of string | Which registered repositories a new ticket includes.<br /><br />This is *what to seed a new ticket with* — a different field from the ticket document's worktree map (*what the ticket has*), not an override pair.<br />Optional. |

## The ticket document

One per ticket, at `.tix/ticket.toml` under the ticket root. Its presence is
what makes a directory a ticket — the discovery walk looks for exactly this
file.

You do not normally write it by hand; `tix setup`, `tix add`, and
`tix remove` maintain it. It is documented because you will read it, and
because a ticket that has drifted from what is on disk is diagnosed by
comparing the two.

### `[ticket]`

The ticket's identity and the worktrees it currently has.

| Key | Type | Description |
| --- | --- | --- |
| `description` | string | A human-readable description of the ticket. |
| `key` | string | A unique identifier for the ticket (e.g. `JIRA-123`). |
| `worktrees` | table of tables | Worktree state, keyed by worktree directory name under the ticket root.<br /><br />Keyed by directory name rather than repo alias so that multiple worktrees of one repository need no schema change; the single-worktree case degenerates to `name == alias`. Each entry records its own branch — there is deliberately no single shared `branch` field, since worktrees share a branch *prefix*, not a branch.<br />Optional. |

#### `[ticket.worktrees.<name>]`

Each entry is a table of its own:

| Key | Type | Description |
| --- | --- | --- |
| `branch` | string | The branch checked out in this worktree. |
| `repo` | string | The alias of the repository this worktree belongs to. |

## Plugin tables

Both documents may carry a `[<plugin>]` table per plugin, and neither tix
nor another plugin validates or rewrites one. They survive every write tix
makes.

A plugin's own configuration is documented by that plugin.
