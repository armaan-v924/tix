Writing a Plugin

A plugin is a program named tix-<name> on your PATH. tix hello runs tix-hello, handing it the context it already resolved. This builds one.

The specification is the contract; this is the shortest path to something that runs.

Read the host context

Section titled “Read the host context”

One call parses the --tix-* flags, answers the print-cli-help handshake, checks the protocol, and exits 125 on a mismatch.

  • Rust
  • Python

user_args is what the user typed, with the host’s flags stripped — feed it straight to your own argument parser. ticket_root is None outside a ticket, which is a normal state rather than an error.

Read your own config

Section titled “Read your own config”

Your plugin owns the [hello] table in either document. Its schema is yours; tix never looks inside.

  • Rust
  • Python

Sections come back as plain dicts, typed as tomllib would type them. An absent section is None.

Write config back

Section titled “Write config back”

Plugins never write the files. You emit a delta, and the host applies it after you exit 0 — against a fresh parse, so it merges with anything written while you ran.

  • Rust
  • Python

Writing no file changes nothing, and so does exiting nonzero.

Where to be careful

Section titled “Where to be careful”

Ignore --tix-* flags you do not recognize. New ones are added without bumping the protocol, and their presence is how you detect a capability.

Do not reimplement -v / -q / --log-level precedence — --tix-log-level is already resolved.

Shelling back out to tix re-discovers the ticket from the working directory, which you may have changed. Pin it:

  • Rust
  • Python

For caches and derived data, use a state directory rather than config — config versus state covers the difference.
