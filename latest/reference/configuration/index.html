Configuration

Every key tix reads, generated from the types it parses the files with.

Both documents are TOML, written through a format-preserving layer: only the value being changed is rewritten, so comments, key order, and plugin tables survive. Unknown keys are an error rather than being ignored.

The global config

Section titled “The global config”

Created by tix config init. Located by --config, then TIX_CONFIG_PATH, then the platform config directory (~/.config/tix/config.toml on Linux, ~/Library/Application Support/tix/config.toml on macOS).

Every key below is addressable as <section>.<key>:

A value is read as TOML when it parses as one and as a string otherwise. List keys take an array literal, or one element at a time:

add creates the list if it does not exist yet and confirms a duplicate (--force skips the question); remove takes one element off, front first, and errors if it is not there. Both keep the array’s layout and comments as written. Keys with a command of their own — tix repo add for [engine].configured_repositories — are still easier reached that way.

[cli]

Section titled “[cli]”

Where tix puts things. Both keys are required.

Key Type Description
code_directory string Where source repositories are cloned: tix repo add derives a new repo’s code_path as code_directory/<alias> (v2 parity).
tickets_directory string Where key-form tix ticket setup creates ticket workspaces, and where id-form --ticket arguments resolve (tickets_directory.join(id)). The default location, not a bound: a path-form tix ticket setup creates outside it, and discovery finds tickets wherever they are.

[engine]

Section titled “[engine]”

The repositories tix knows about. Maintained by tix repo add.

Key Type Description
configured_repositories table of tables Source repositories registered by the user, keyed by alias.
Optional.

[engine.configured_repositories.<name>]

Section titled “[engine.configured_repositories.<name>]”

Each entry is a table of its own:

Key Type Description
code_path string The path to the code directory of the repository.
remote string The remote URL of the repository.

[defaults]

Section titled “[defaults]”

Read once, when a ticket or worktree is created, then recorded in the ticket document — changing one never rewrites an existing ticket. See creation-time seeds. Every key is optional.

Key Type Description
branch_prefix string Seed for branch name derivation at tix ticket setup: <prefix>/<key>-<sanitized-description>.
Optional.
default_repository_owner string Seed for remote URL construction: the owner used when a repository is given without one.
Optional.
github_base_url string Seed for remote URL construction.
Optional.
repositories array of string Which registered repositories a new ticket includes.

Seeds a new ticket. The ticket document’s worktree map records what a ticket actually has; changing this leaves existing tickets alone.
Optional.

The ticket document

Section titled “The ticket document”

One per ticket, at .tix/ticket.toml under the ticket root. Its presence is what makes a directory a ticket. tix setup, tix add, and tix remove maintain it; it is documented because you will read it.

[ticket]

Section titled “[ticket]”

The ticket’s identity and the worktrees it currently has.

Key Type Description
description string A human-readable description of the ticket.
key string A unique identifier for the ticket (e.g. JIRA-123).
worktrees table of tables Worktree state, keyed by worktree directory name under the ticket root.

Keyed by directory name so that multiple worktrees of one repository need no schema change; the single-worktree case degenerates to name == alias. Each entry records its own branch, since worktrees in a ticket share a branch prefix rather than one branch.
Optional.

[ticket.worktrees.<name>]

Section titled “[ticket.worktrees.<name>]”

Each entry is a table of its own:

Key Type Description
branch string The branch checked out in this worktree.
repo string The alias of the repository this worktree belongs to.

Plugin tables

Section titled “Plugin tables”

Both documents may carry a [<plugin>] table per plugin. tix has no schema for one, and they survive every write it makes. tix config set <plugin>.<key> reaches one like any other section, writing the value as given — there is no type to check it against. A plugin’s configuration is documented by that plugin.
